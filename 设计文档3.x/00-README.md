## 3 事实源与冲突处理

需求和范围以01为准；交互协议以06及11中的同名DTO为准；目标物理结构以05为准。06只引用11的DTO，不重复发明字段。04的参考函数必须遵守11的公式。发现冲突即阻断对应功能冻结并同步修订，不用“DDL永远优先”把需求缺口隐藏掉。

05 描述的是目标结构：原库52表只作为迁移起点，本版新增9张工程/组织表，目标61表。旧536字段/69外键只是历史计数；目标列数、外键与索引数量在生成并通过双方言校验后由机器输出，不手填承诺。不能把旧初始化脚本当作3.2.0最终DDL执行。

## 4 术语与时间

六维：`content/expression/posture/interaction/board_ppt/time_management`；六类人设：`focused/active/distracted/challenger/quiet/naughty`。事件枚举使用`distracted/noisy`，不用`distract/noise`。

业务API前缀统一`/api/v1`；运维`/health/*`与内部`/internal/*`按06原路径，属于明确例外；WS为`/ws/sessions/{session_id}`。报告查询路径参数为session_id；报告内部仍有稳定report_id。绝对时间UTC，界面显式“北京时间”。计时/音视频offset均采用排除暂停的活动时间轴；计划时长用秒。

`allow_retry=3`表示首讲+3次重做，共4次已开始的正式场次；aborted也消耗一次，未start的草稿不消耗。正式任务题目、模式、时长、评分标准由服务端绑定。

## 5 部署与验收层次

| 形态 | 运行方式 | 可证明的内容 |
|---|---|---|
| A1单机 | Python3.12单API+同进程后台调度，MySQL8，本地文件；运行态可memory | 单场完整业务闭环；SQL持久化仍必需；重启恢复由数据库恢复器负责 |
| A2单机Redis | A1+Redis7+AOF，arq独立worker | 队列、租约、重启恢复和多worker验证 |
| B正式 | 6个服务可独立进程，MySQL/SQL Server二选一，Redis队列、对象存储、HTTPS、TURN | 经测试确认后的多用户能力，不预先承诺200场 |

采集5秒切片与S3上传part分层；记录完逐轨complete，再session submit触发评测。所有形态都走同一接口；upload_mode只选择local_parts或s3_multipart传输。

## 6 状态声明与门禁

必须完成的实施门禁：G1双方言DDL新建与升级；G2真实10分钟媒体闭环；G3实际账号模型能力、长音频分段和时间锚点；G4权限/故障恢复/改分联动；G5至少50份固定样本效果验收；G6目标环境并发/媒体带宽/SLA。详见12。

当前设计条款已改写，G1–G6均没有被本次文档任务执行。各门禁可以并行推进，但不能用一次10秒模型连通替代G2/G3/G5/G6。可先做组织管理、页面骨架和DTO实现；未过门禁的能力只能标“待验证”。
